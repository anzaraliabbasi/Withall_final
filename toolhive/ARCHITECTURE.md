# ARCHITECTURE — ToolHive

> How the system is designed, how it flows, and where every file lives.

---

## 1. High-Level Architecture

```
                    ┌──────────────────────────────────────────────┐
                    │              STATIC HOSTING (CDN)              │
                    │        Vercel / Netlify / Cloudflare          │
                    │  - 128 prerendered pages (SSG)                │
                    │  - per-tool JS chunks, lazy-loaded            │
                    └───────────────────┬──────────────────────────┘
                                        │ HTTPS (static files only)
                                        ▼
                    ┌──────────────────────────────────────────────┐
                    │                 USER'S BROWSER                 │
                    │                                              │
                    │  Next.js App Router + React 19 runtime       │
                    │  ├── Tool page shell (SEO content, FAQ)       │
                    │  └── ONE tool component, lazy-loaded ────────┼───┐
                    │                                              │   │
                    │  ┌───────────────────────────────────────┐   │   ▼
                    │  │           CLIENT-SIDE ENGINES          │   │ ┌─────────────────┐
                    │  │ • Canvas 2D API     (image tools)     │   │ │ INSTALLED LIBS  │
                    │  │ • Web Crypto API    (SHA-1/256/384/512│   │ │ pdf-lib  (PDF)  │
                    │  │   + in-file MD5/SHA-224)              │   │ │ qrcode   (QR)   │
                    │  │ • File/Blob API     (uploads→memory)  │   │ │ jsbarcode      │
                    │  │ • html-to-image      (mockup→PNG)      │   │ │ html-to-image  │
                    │  │ • DOM/SVG            (CSS/SVG tools)  │   │ └─────────────────┘
                    │  └───────────────────────────────────────┘   │
                    └──────────────────────────────────────────────┘

   NO APPLICATION SERVER. NO DATABASE. NO FILE STORAGE.
   Nothing the user types or drops is ever transmitted anywhere.
```

**Key decision:** because every tool is client-side, the "backend" is just static files on a CDN. That gives:

- privacy by architecture (not policy),
- ~zero marginal cost per user,
- near-instant tool execution (no network round-trip),
- offline resilience (a loaded tool works with the network off).

## 2. App Flow

### 2.1 Visitor → tool → result (primary flow)

```
Google search "whatsapp chat generator"
        │
        ▼
/tools/whatsapp-chat-generator        ← SSG page, unique title/description/FAQ/JSON-LD
        │   ┌──────────────────────────────────────────────┐
        │   │ ToolRenderer(slug)                            │
        │   │   └─ registry[slug] = dynamic(import(...))    │ ← per-tool chunk loads
        │   │        └─ user interacts: types, uploads,     │
        │   │           drags sliders                      │
        │   │            → live re-render of preview       │
        │   │            → Download button → Blob → save  │
        │   └──────────────────────────────────────────────┘
        ▼
result on user's disk. nothing ever left the browser.
```

### 2.2 Discovery flows
- **Home** → category sections → tool card → tool page.
- **Header search** → live fuzzy match on name/slug → click → tool page.
- **Category hub** (`/pdf-tools`, `/social-media-tools`, …) → tool card.
- **Tool page footer** → related tools in same category.

### 2.3 Build-time flow (what `npm run build` does)
1. `tool-names.json` (117 entries) is imported by `lib/tools.ts`.
2. `app/tools/[slug]/page.tsx` runs `generateStaticParams()` → **117 tool pages prerendered**.
3. `app/[category]/page.tsx` → **9 category pages** prerendered.
4. `sitemap.ts`, `robots.ts`, `manifest.ts` emit `/sitemap.xml`, `/robots.txt`, `/manifest.webmanifest`.
5. All tool components compiled into **separate lazy chunks** via `components/tools/registry.ts` (auto-generated by `scripts/gen-registry.py`).

## 3. Technology Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | **Next.js 15 (App Router)** | SSG for 128 SEO pages, per-route code splitting, one-command deploy |
| UI | **React 19** | Concurrency, stability |
| Language | **TypeScript (strict)** | Tool inputs/outputs are typed end-to-end |
| Styling | **Tailwind CSS 3.4** | Utility-first, dark mode via `class` strategy, tiny CSS |
| Fonts | `next/font` (Inter) | Zero CLS, self-hosted at build |
| PDF engine | `pdf-lib` | Merge/split/edit/sign fully client-side |
| QR / barcode | `qrcode`, `jsbarcode` | Battle-tested, canvas/SVG output |
| Mockup export | `html-to-image` | DOM → PNG at 2× pixel ratio |
| Hashing | Web Crypto API (+ in-file MD5/SHA-224) | Native speed; no server, no library for the standard digests |
| Hosting | Vercel (default) | Zero-config Next.js static output |

**Runtime "engines"** (browser APIs the tools rely on): Canvas 2D, Web Crypto, File/Blob/URL.createObjectURL, DOMParser (SVG tools), `document.fonts` (handwriting tool).

## 5. Data model

`tool-names.json` entry (the only "database"):

```json
{
  "slug": "qr-code-generator",
  "name": "QR Code Generator",
  "category": "misc",
  "seoTitle": "Online QR Code Generator: Free & Unlimited | ToolHive",
  "shortDesc": "QR Code Generator — free, fast and unlimited. Runs entirely in your browser."
}
```

- `slug` = URL (`/tools/<slug>`) **and** file name (`components/tools/<folder>/<slug>.tsx`).
- `category` = one of 9 ids defined in `lib/categories.json` (name, url slug, icon, description).
- The component registry, sitemap, category pages and search are ALL derived from this one file — add a row + a component and the whole site updates.

## 7. Performance & security notes

- **Bundle:** shared First Load JS ≈ 103 kB; each tool chunk loads on demand.
- **Lazy loading:** `registry.ts` maps every slug to `next/dynamic(() => import(...), { ssr: false })` so heavy libs (pdf-lib etc.) are only fetched on that tool's page.
- **XSS:** all tool output is rendered as text nodes / canvas / SVG in DOM (never `dangerouslySetInnerHTML` with user input — the only usage is a build-time JSON-LD script we generate ourselves).
- **File safety:** dropped files live in memory as `Blob`/`ArrayBuffer`; object URLs are revoked after download.
- **Secrets:** none exist — there are no API keys anywhere in this project.
